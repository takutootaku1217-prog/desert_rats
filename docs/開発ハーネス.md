# 開発ハーネス

既存Godot診断を1プロセスずつ実行する `tools/run_checks.py`。Python 3.10以上・標準ライブラリのみ。インストール・Git更新・commit・push・既存ファイルの削除は行わない。Godotのimportは `.godot` キャッシュ等を生成する。

## 実行

リポジトリのルートで実行する。Godot実行ファイルはPATHの `godot` / `godot4`、または `--godot` にファイルのパスを指定する。

```sh
# 通常の生活循環（地点1本＋既存6本＋新規2本＋長時間2条件＋起動）
python tools/run_checks.py --suite core

# 手動運搬併用・出来事あり。現在は既知の不合格があり、終了コード1になる
python tools/run_checks.py --suite extra

# 修正後に指定診断だけ再実行。前の結果は上書きしない
python tools/run_checks.py --check cargo_reservations --check consumption_loop

# 出力先・実行ファイルを指定（パスに空白があれば引用符で囲む）
python tools/run_checks.py --check items --godot /usr/local/bin/godot --output-dir /tmp/desert-rats-harness

# 目的地型採取スポットの境界条件と20分滞在
python tools/run_checks.py --check quarry

# 一覧とハーネス自身の診断
python tools/run_checks.py --list
python tools/test_run_checks.py
```

`--check` 指定時はその診断だけを対象とし、通常セット全体は実行しない。どの場合も先頭にimportを自動で1回入れる。importが失敗したら後続は `not_run` になり、全体も非ゼロ終了する。診断単体の失敗は記録して次の診断へ進む。

既定の保存先はOSの一時フォルダ内 `desert-rats-harness/`。各実行でUTC日時＋一意な名前のサブフォルダを作る。長期保存にはリポジトリ外の永続ディレクトリを `--output-dir` で指定する。一時フォルダはOSによって消去され得る。証拠自体をソース変更と誤判定しないため、リポジトリ内への出力指定は受け付けない。

Windowsのパス例（**このOSでの動作は未検証**）:

```powershell
python tools/run_checks.py --check items --godot "C:\Tools\Godot\Godot.exe" --output-dir "C:\GodotChecks"
```

タイムアウトは各診断の実時間でimport120秒、単体180秒、長時間診断300秒。必要に応じ `--timeout 600` で全選択診断の上限を変更できる。これはプロセス終了の上限で、ゲーム内の完成品待ち60秒判定を変えるものではない。

## 結果の見方

実行末尾に `results.json` の場所を表示する。

- `status`: 選択した全診断が成功した場合のみ `passed`。通常セットが通っても追加セット・全プレイ条件の合格ではない。
- `checks`: コマンドはシェル文字列ではなく引数配列。標準出力と標準エラーを同じ `<診断ID>.log` に保存する。終了コード0でも `ERROR:` / `SCRIPT ERROR:` / `FAIL` / `★` がある、または診断の完了マーカーがない場合は `failed`。
- `timeout` / `missing_executable` / `launch_error` / `interrupted` / `not_run`: いずれも合格扱いしない。全体の終了コードは1。引数自体が不正ならargparseの終了コード2。
- `first_failure`: その実行の最初の失敗。後の成功・失敗で書き換えない。再実行は別フォルダになり、古いログ・JSONは保持する。
- `metadata`: OS、Python、Godotバージョン、HEAD、ブランチ、dirty状態、変更ファイル名とSHA256、ランナー起動引数。環境変数や認証値は記録しない。
- `git_before` / `git_after`: 途中でHEADやソース状態が変化したら全体を不合格にする。診断中はソースを編集しない。dirtyでも状態を記録して検証できるが、その結果をHEADだけの検証と混同しない。
- `elapsed_wall_seconds`: ランナーが測った実時間。`requested_game_minutes_per_run` / `requested_repetitions` は要求したゲーム内時間。実際に完走したかはログの結果を見る。固定fps・倍速のため両時間を同一視しない。

進行中も各診断後にJSONを保存する。ランナー自体を強制終了した場合は `running` / `not_run` のまま残ることがあり、成功とは扱わない。POSIXではタイムアウト時に子プロセスグループを停止する。Windowsでは直接起動したGodotプロセスを停止する実装で、子孫プロセスの一括停止は未保証。

## 診断の追加

`tools/run_checks.py` の `CHECKS` に `Check` を追加し、必要な `SUITES` にIDを加える。既存の `test_*.gd` は `diagnostic("名前")` で登録できる。成功マーカー・実時間タイムアウト・必要ならゲーム内の要求時間を明示する。引数はタプル／リストで持ち、`shell=True` やシェル文字列連結を使わない。

追加後は `python tools/test_run_checks.py` と `--check <ID>` を実行する。ハーネス自身の診断は、成功、非ゼロ終了、終了0でもエラー／未完了、タイムアウト、実行ファイル欠如、未実行、空の実行計画、空白等を含む引数、再実行時の履歴保持を模擬コマンドで確認する。

## 現在の範囲と既知の不合格

Linux / Godot4.6.3で確認。Windows / Godot4.7.2・OSクリック操作・音声は未確認。

- `core`: 出来事を止めた通常初期状態32ゲーム内分×2と、診断用の全設備状態28分×2を含む。全条件の安定・生存を保証するセットではない。
- `extra`: 内蔵エンジン化後の手動運搬併用seed701は担当不在最大60.8ゲーム内秒で既存基準により失敗する。有限待ちは無期限停止と区別してトレースへ記録する。機関室ありの旧配置では手動60.4秒・出来事あり62.6秒だったが、現行配置の結果と混同しない。失敗はそのまま非ゼロ終了・JSONに残し、既知失敗を自動で合格にしない。
- 出来事ありは内蔵エンジン化後の再実行でゲーム内1307.8秒に襲撃でゲームオーバー（旧配置の記録は1666.6秒）。休憩・緊急修理・迎撃の優先方針は未決定事項。数値・休憩・戦闘仕様は変更していない。現行の配置変更と検証は `docs/内蔵エンジン化と採取スポット調査_2026-10-11.md`。
- `GameData.ENABLE_COMBAT=false` は一定間隔で敵が出る**旧方式**を停止する設定。別系統の出来事による襲撃は `ENABLE_RAIDS=true` で有効。両方を「戦闘全体が無効」と読み替えない。

正式診断名・再現前後・通し条件・待ちとゲームオーバーの根拠は `docs/採取加工消費_検証記録_2026-10-11.md` にある。

目的地型採取スポットの実装範囲・調整値・回帰結果は `docs/目的地型採取スポット_実装記録_2026-10-11.md`。coreはimport込み13項目。新しい地点での成功と、従来の襲撃/手動併用の不合格を分けて扱う。

6区画化の回帰は `python3 tools/run_checks.py --suite layout`。部屋・外装・カメラ・ドット密度と、加工室/倉庫を後方へ移した採取地点循環を含む。coreには自動追加されないので配置変更時は両方を実行する。
