# Claude向け独立検証依頼: 仲間状態・退却・燃料漏れ

対象リポジトリの `main` で、仲間の状態表示／個人退却／手動修理とエンジン燃料漏れの完成ループを独立に確認してください。既存のユーザーセーブ・stash・未コミット変更を消さず、検証用の `APPDATA` と出力先を分離してください。

## 採用仕様

- 敵攻撃は既存HULLだけでなくDRIVEにも損傷を与える。DRIVE < 70 で燃料漏れが始まる。低速ほど少なく、停止中もゼロにはならない。経時だけで壊れる新仕様はない。
- 漏れは標準速度60・最大損傷で0.045 fuel/s、損傷係数35%〜100%、停止係数25%。修理キット1個、既存の1.2秒、耐久+25。
- DRIVE 30未満の攻撃時には目標速度を既存速度上限40へ下げる。修理で自動復帰させず、プレイヤーが手動で目標速度を戻す。
- HUDは漏れ量、減速／停止の意味、修理キットの必要数・所持数・不足数、担当を示す。都市または既存の応急即時修理は残し、仲間への現地修理依頼とは別である。
- 仲間詳細は実際のAI状態（採取、運搬、加工、戦闘、食事、修理、休息、負傷、帰還）を読む。退却と修理待ちは実状態に重ねて表示する。
- 「退却命令」は戦闘・食事・休息・修理中でも安全に中断して帰還させ、新規接敵・採取・再戦を止める。解除UIがあり、解除するまで保持される。無敵化・瞬間移動はない。
- 手動修理は個人指定または「適任に修理を依頼」で初期3人の誰でも行える。終了時は既存優先度AIに戻る。資材不足・取消・退却・負傷・戦闘・保存復元で予約、荷物、注文を二重消費／消失させない。

## 必須確認

1. `python tools/run_checks.py --check trouble_loop --godot <Windows Godot 4.7.2 exe> --output-dir <repo外>` をAPPDATA隔離で実行し、importと新規テストを成功させる。
2. 既存の `field_operations`、`manual_combat`、`life_actions`、`save_game`、`crew_detail`、`haul_flow`、`order_flow` を実行し、既存の回収・配達・燃料前渡し・全パーツ修理、荷物・注文予約が回帰していないことを確認する。
3. coreを全件実行し、最終ソース状態のまま成功することを確認する。
4. 実Rendererで以下を目視確認する。
   - `docs/trouble-loop-evidence-2026-10-18/trouble-hud.png`: 漏れ、停止中も漏れる注記、修理依頼導線。
   - `docs/trouble-loop-evidence-2026-10-18/trouble-crew.png`: 状態、退却命令、修理を任せる導線。
5. 可能なら隔離セーブでOS入力も確認する。未実施ならViewport入力と実Renderer検証と区別して記録する。

## 期待される不変条件

- 修理取消／退却／負傷時に修理キットが二重消費されず、`repair_reserved` と `refuel_reserved` に古い担当が残らない。
- 退却中は `return_request` が保持され、`order_attack` とAIの新規戦闘開始が拒否される。
- 食事中の退却では `food_claims` を解放し、携行食を倉庫へ戻す。
- 旧セーブで `return_request` と `manual_job` がない場合は読み込める。新しい値は `manual_job in [-1, REPAIR]` のみ許可する。
- 保存後の退却＋修理待ちでは、修理指示を保持しても古い部位予約が復元されない。

問題があれば、再現手順、対象状態、所持／予約数、保存前後の差分、テストログを添えて報告してください。仕様を勝手に拡張せず、数値を変えるなら上記仮値と既存設定への影響を明記してください。
