# 見落としを減らすQA依頼プロンプト（砂漠の移動拠点用・改訂第2版 2026-10-02）

元の汎用版を、このプロジェクトで実際に起きた見落とし・取り違えの事例をもとに改訂したもの。改訂の理由は末尾の「改訂で足したこと」。

## 依頼する前に（依頼する側の準備）

1. **対象をGitHubに上げる。** ローカルにしかないコミットは、QA側からは見えない（`git log origin/main..HEAD` が空でなければ未push）。上げずに依頼すると、QA側は古い版を調べ、直した不具合を「未修正」として報告してしまう。
2. **GitHub側のSHAを確かめる。** `git ls-remote origin refs/heads/main`（ブランチ名は対象に合わせる）の40桁が、手元の `git rev-parse HEAD` と一致することを確認する。
3. **未コミット変更がないことを確かめる。** `git status --short --untracked-files=all` が空であること。手元にだけある変更はSHAに含まれず、QA側には届かない。QAに含めたいなら、先にコミットしてpushする。
4. 下の依頼文の【記入欄】を埋める。対象は**完全なSHA（40桁）**で固定する（ブランチ名は参考情報。ブランチの先端はpushのたびに動く）。
5. 今回の依頼で確定させたい仕様があれば【今回の確定仕様】に書く（対象版の CLAUDE.md や設計書より優先される）。
6. 前回のQA報告書があれば添付し、前回の対象SHAも書く（直ったかの再確認と、変更箇所の重点調査になる）。

## 依頼文（コピー用）

```text
あなたはQAエンジニア兼グラフィックデバッガーです。
対象：砂漠の移動拠点（Godot 4 / GDScript）

【記入欄】
- リポジトリ：https://github.com/takutootaku1217-prog/desert_rats
- 対象コミットSHA（必須・完全な40桁。対象はこのSHAで固定）：〈ここに記入〉
- 取得元のブランチ／PR（参考情報。先端が動いていてもSHAを優先）：〈ここに記入〉
- 許容する検証環境：〈例: Godot 4.7.2 必須／Godot 4.x なら可（版の差を明記）〉
- 今回の確定仕様（CLAUDE.md・設計書より優先）：〈なし／箇条書き〉
- 前回QAの対象SHA・報告書：〈なし／SHAと添付〉
- 重点領域：〈全体／例: 背景・カメラ〉
- 対象外：〈例: 戦闘（ENABLE_COMBAT=false で無効）〉

目的は描画・カメラ・UI・機能の不具合を発見し、再現して報告することです。
今回は修正しません。ゲームコードの変更、コミット、push、ブランチ・PRの作成、公開設定の変更は禁止です。
検証用スクリプト、ログ、画像、報告書はリポジトリの外へ保存してください。

0. 対象版と検証環境の確定（一致しなければ検証を始めない）
- 対象はブランチ名ではなく、記入欄の完全なSHA（40桁）で固定します。
- 依頼者の作業フォルダは使わず、対象SHAから隔離した検証用フォルダを用意してください。
  例: git clone <リポジトリ> <隔離フォルダ> → cd <隔離フォルダ> → git checkout --detach <対象SHA>
  依頼者の作業フォルダの git worktree（元の .git に記録が残る）や、作業フォルダのコピー（未コミット変更や
  .godot の生成物が混ざる）は使わないでください。Godot の --import と実行は、隔離フォルダの中だけで行ってください
  （.godot/・*.uid・*.import が生成されるため）。
- 依頼者の作業フォルダにアクセスできる場合は、何かを始める前に、そのフォルダの git rev-parse HEAD と
  git status --short --untracked-files=all を記録してください。
- 隔離フォルダで、--import の前に git rev-parse HEAD（完全なSHA）と git status --short --untracked-files=all を記録し、
  ① HEAD が対象SHAと完全に一致する ② 未コミット変更・未追跡ファイルがない
  の両方を確認してください。SHAが一致していても、未コミット変更があれば中身が違うため、一致とみなしません。
- Godot の実バージョン、OS、描画ドライバー、画面サイズを記録し、記入欄の「許容する検証環境」を満たすか確認してください。
- 対象SHAを取得できない、HEAD・作業ツリー・検証環境のどれかが一致しない、のいずれかなら、検証を始めないでください。
  何がどう違うか（期待した値と実際の値）を報告して止まってください。別の版や別の環境で代わりに調べないでください。
- 基準環境は Godot 4.7.2 / Windows です。許容範囲内で版・OS・ドライバーが違うときは、
  その差で起き得る指摘（描画・カメラのスムージング・入力）に「環境差の可能性」と付けてください。

1. 仕様の把握と優先順位
- 仕様の優先順位は ①この依頼文の【今回の確定仕様】 ②対象SHAに含まれる CLAUDE.md です。
  ①と②が食い違うときは①に従って判定し、食い違いそのものも「仕様確認」として報告してください。
- この優先順位で決まらない食い違い（CLAUDE.md の中の記述どうし、CLAUDE.md と docs/ の設計書、
  コードのコメントと CLAUDE.md など）は、どちらかに決めず、両方を引用して「仕様確認」として報告してください。
  日付の新しい記述を勝手に正としないでください。
- ブランチごとに仕様が違います（例: 遠征やスタミナを撤去したブランチがある）。対象SHA以外の版の仕様を持ち込まないでください。
- 対象版の CLAUDE.md を読み、機能ごとに「現行仕様／未実装／廃止済み／要確認（仕様・数値が未決定）」に分けた表を作ってください。
- CLAUDE.md の「要確認」「今後の仕様（保存だけ）」「未着手」の内容と、docs/ の設計書の未実装部分は、
  不具合ではなく「仕様確認」に分けてください。
- 前回の報告書があれば、指摘IDごとに対象版で直っているかを、実際の画面と操作で再確認してください。
  コミットメッセージ・修正ログ・既存診断の成功だけで「修正済み」と扱わないでください。
- 前回の対象SHAがあれば git diff <前回SHA>..<対象SHA> --stat を確認し、変更箇所とその周辺を重点的に調べてください。

2. 準備と既存診断（すべて隔離フォルダで）
- 最初に Godot --headless --path . --import を1回実行してください（class_name の登録。しないとスクリプトが読めません）。
- 起動確認として Godot --headless --path . --quit-after 300 の error / warning を記録してください。
- scripts/main.gd と、実際のメインシーンのスクリプト 砂漠のネズミ団.gd が同一か（ハッシュ）を確認してください。
- 既存診断 tools/test_*.gd は、Godot --headless --path . -s res://tools/<名前>.gd で1本ずつ、
  Godot を同時に複数動かさずに実行し、最終行（「すべて成功」または「N 件失敗」）まで確認してください。
  実行中・途中までの出力を成功扱いしないでください。出力は末尾だけに切り詰めず、失敗した項目名が分かる形で全文を保存してください。
- 診断が失敗したら、その出力を消さずに残したうえで、単独で再実行してください。各回について、実行条件
  （同時に動いていたGodotなどのプロセス、--fixed-fps の有無、Engine.time_scale、乱数の種）と結果を記録してください。
- 再実行で成功しても、最初の失敗は消さないでください。「毎回失敗／n回中m回失敗／最初の1回だけで以後は再現せず」と
  再現性を書き、「不安定な診断」として報告に残してください。「その後3回成功した」ことだけで問題なしと断定しないでください。
  --fixed-fps なしのヘッドレスは実時間に依存するため負荷で揺れることがありますが、揺れだと推測しても、原因が確かめられるまでは推測として書いてください。
- 既存診断は既知の範囲しか見ていません。成功しても、以下の試験を省略しないでください。

3. 調査の分割
- 次の領域ごとに、通常操作・境界条件・機能間の組み合わせの確認表を作ってください。
  A 背景・カメラ・重なり順（視差スクロール・追従・デッドゾーン・外装/内装の切り替え・天候の重ね絵）
  B UI・入力（上部カード・右上パネル・各画面のキー B/R/P/C/F/Tab/X/O/I/Esc/↑↓ など・ツールチップ・クリック選択）
  C 在庫・制作・搬送・積載重量（倉庫と作業場・手動の制作・建設の依頼と材料の取り置き・満杯で捨てる処理）
  D 仲間AI・ステータス・中断（HP・満腹度・疲労度など・休憩と食事・戦闘不能・遠征・部屋の移設）
  E 拠点の維持と出来事（燃料・耐久・天候・襲撃・故障・ゲームオーバーとやり直し）
- 確認表の列: ID／領域／条件／手順／期待結果／実際の結果／証拠／確認方法／状態（正常・不具合・要仕様確認・未検証）。
- 1領域を終えるたびに確認表をファイルへ保存してから次へ進んでください（途中で中断しても続きから再開できるように）。
- 複数担当を使える場合は領域で分担し、最後に別担当が主要な指摘の証拠を確認してください。

4. 境界条件と組み合わせ
- 空・満杯・容量直前（積載重量）、低HP・低満腹度・高疲労度、複数人の同時作業、
  UIを開いたままの在庫変化、押下中の画面更新、複数メニューの切り替えを含めてください。
- 移動・登攀（ハシゴ・斜路）・搬送・食事・休息・加工の途中での、遠征・中断・部屋の移設・外装への切り替えと、
  その後の次の行動まで確認してください。瞬間の位置だけでなく、その後の推移を見てください。
- 倉庫・作業場・運搬中（仲間が持っている分）・加工設備の中の合計数量、重量、予約、状態遷移を、
  操作の前後で観測してください（予約の取り残し・二重取得・物の消失・スクリプトエラー）。

5. 描画の確認（ウィンドウ表示の実際の描画で。ヘッドレスの結果で画面を検証済みにしない）
- 標準の 1280x720 に加え、異なる縦横比、整数倍でない窓の大きさで調べてください。
- カメラの端（左右に大きくパン）、追従対象の切り替え、時間経過（走行で背景が一周する前後）を含めてください。
- 欠け、継ぎ目、重なり順（仲間・資源・採取ポイント・生物・車体）、天候の覆い、カメラの急変と滑らかさを確認してください。
- カメラの表示位置は Camera2D.position（目標値）ではなく、viewport の canvas transform から実際の値を求めてください
  （内蔵スムージングで遅れるため）。
- 撮影は --windowed --resolution 1280x720 で行い、時間を揃えるときは --fixed-fps 60 を付け、付けたかを記録してください。
  極端に小さい固定FPS（2〜4）での異常はストレス条件として分け、通常プレイの不具合と混同しないでください。

6. 入力の確認（OSレベルの実際の操作で。ヘッドレスの結果でクリック操作を検証済みにしない）
- クリックとキー入力は、ウィンドウ表示とOSレベルのマウス・キー操作で、実際の入力配送により確認してください。
  ヘッドレスの Input.parse_input_event ではマウス位置が更新されないため、クリック判定の検証になりません。
- 実際の操作ができない環境では「未検証」とし、判定の関数だけを直接確かめた場合は「診断スクリプト」と明記してください。
- スクロール可能な画面外の内容を、欠落と誤認しないでください。

7. 再現と判定
- 候補には最小再現手順を作り、条件を1つだけ変えた正常対照と、再実行で確認してください。
- 再現のために設定した初期状態（FacilityDB.start_all、出来事の有効/無効、乱数の種、Engine.time_scale、
  止めた処理）を明記し、通常プレイでも起き得るかを分けて書いてください。
- queue_free が次のフレームまで実際には消えないなど、エンジンの遅延処理を観測の誤差と取り違えないでください。
- 仮想画面・ドライバー・人工的な時刻設定の問題を、通常プレイのバグと混同しないでください。

8. 最終報告
- 日本語で、リポジトリの外に保存してください。
- 冒頭に、確認した対象SHA（完全な40桁）、隔離フォルダの作業ツリーの状態、環境（Godot版・OS・ドライバー・画面）、
  記入欄との差、既存診断の結果一覧（不安定だった診断と各回の結果を含む）を書いてください。
- 「再現済みの不具合」「コード読解だけの候補」「仕様確認が必要な点」「不安定な診断」「前回指摘の再確認結果」「未検証の範囲」に分けてください。
- 確認方法は次の5つで区別してください。
  実画面確認＝ウィンドウ表示の実際の描画を画像で確認した
  実操作確認＝OSレベルのマウス・キー操作で確認した
  診断スクリプト＝ヘッドレスの自己診断や、独自の検証スクリプトで確認した
  コード読解のみ＝コードを読んだだけで、動かしていない
  未検証＝確認できていない
  ヘッドレスの診断スクリプトで確かめた項目を、画面やクリック操作の「検証済み」にしないでください。
- 各指摘に: ID（領域の頭文字と番号。例 BG-05・CAM-03・UI-01・INV-02・AI-04）、
  重要度（P1=主要な表示・操作を大きく損なう／P2=通常の表示・操作に影響／P3=品質・調整）、
  発生箇所（ファイル:行）、条件と手順、期待結果、実際の結果、推測原因、影響、証拠（画像・ログ・再現スクリプトのパス）、
  確認方法（上の5つのどれか）を記載してください。
- 正常だった条件も書いてください。テストが通った範囲から「バグは残っていない」と一般化しないでください。
- 依頼者の作業フォルダにアクセスした場合は、作業前と作業後の git rev-parse HEAD と git status --short --untracked-files=all を
  並べて示し、変わっていないことを確認してください（隔離フォルダの変化は対象外）。アクセスしていない場合はその旨を書いてください。
- 発見後の修正は、別途依頼するまで行わないでください。
```

作業が大きくなると、調べる範囲・状態の組み合わせ・前提の数が増え、確認漏れの可能性も上がる。処理負荷そのものより、対象版の取り違え、途中で変わった仕様、成功した既存診断への過信、機能の中断や競合の未検証が原因になりやすい。この依頼文は、それらを具体的な確認事項に分解する。見落としをゼロにする保証ではない。

## 改訂で足したこと（このプロジェクトで実際に起きたこと）

### 第1版（2026-10-02）

| 足したこと | 理由（実際に起きたこと） |
|---|---|
| 依頼前の準備・記入欄の必須SHA | 依頼文を作った時点では、GitHubの `main` は修正前の `b5bb0b6` で、修正済みのコミットはローカルだけだった。未統合の `gpt/` ブランチも2本あり（うち1本は遠征とスタミナを撤去済みで仕様が違う）、別のフォルダには未pushの作業もあった。版を取り違える条件がそろっていた |
| 基準環境（4.7.2 / Windows）と環境差の付記 | 前回のQAは Godot 4.6.3 / Linux / 仮想画面で行われ、低FPSでのカメラの発散は版や環境の差の可能性が残った |
| 作業用の複製で作業し、最後に元の `git status` を示す | Godot を実行すると `*.uid`・`*.import` が生成され、未追跡のファイルが7つ溜まっていた |
| 仕様確認に回すもの（CLAUDE.mdの「要確認」・docsの設計書） | `docs/第1ワールド設計` は設計書だけで実装はゼロ。未実装を不具合として報告しないため |
| 前回指摘の再確認・差分の重点調査 | BG-01〜04・CAM-01/02 を直した（1aeaa55）。直ったかの確認と、修正の副作用（y-sort・出現位置・クリック範囲）の確認が要る |
| `--import` を先に・診断は1本ずつ | `--import` なしでは新しいクラスが読めない。Godot を同時に複数動かした回だけ診断が失敗したことがある |
| 表示位置は canvas transform から・低FPSはストレス条件 | 前回の報告書の良かったやり方を、決まりとして残した（Camera2D.position は目標値で、実際の表示は遅れる） |
| ヘッドレスではクリックの検証にならない | `Input.parse_input_event` ではマウス位置が更新されないことを確認済み。判定の関数（`Main._pick_worker_at` など）の確認と、実際のクリックは別物 |
| 領域E（燃料・出来事・ゲームオーバー）、Aに重なり順、Dに部屋の移設 | 元の4領域に入っていなかった機能 |
| 運搬中を含む合計数量・スクリプトエラーの観測 | BG-03 を直した結果、採取中の採取ポイントが消える経路ができ、解放済みのオブジェクトを参照するエラーが出た（その場で修正済み） |
| `queue_free` の遅延の注意 | 自己診断を書いたとき、消えたはずの物が同じフレームではまだ有効で、誤った失敗になった |
| 指摘ID・確認方法の列 | 修正のコミットと指摘を対応づけるため |

### 第2版（2026-10-02、補強）

| 足したこと | 理由（実際に起きたこと） |
|---|---|
| 対象は完全なSHAで固定し、ブランチ名は参考情報にする | ブランチの先端はpushのたびに動く。このリポジトリでも、QA報告書の対象（`b5bb0b6`）と、その後の `main` の先端は別のSHAになった |
| SHAが一致しても、未コミット変更・未追跡ファイルがあれば一致とみなさない | 同じSHAでも作業ツリーが違えば中身が違う。実際に、コミットされていない `.uid`・`.import` や設計書が作業フォルダに残っていたことがある |
