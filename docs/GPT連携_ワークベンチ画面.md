## 1. このプロジェクトについて（要約。詳細は CLAUDE.md）

- Godot 4（GDScript）で作っている、「砂漠のネズミ団」風の**オリジナル**の放置ストラテジーゲーム。原作の画像・名前・キャラは一切使わない。
- ユーザーの環境は Godot 4.7.2（Windows）。コードは 4.3 以上で動く書き方にする。
- 現在は「検証段階」。実際に遊んで違和感を見つけ、指示された範囲だけを直す進め方（先回りの機能追加は禁止）。
- UIの方針: 文字を大量に並べない。アイコン・色・数量で状態が一目で分かることを優先する（「アイコンそのものがゲージ」など）。
- 将来、絵は高品質な2Dドット絵に差し替える前提（今の絵は仮素材）。**コードで図形を描かず、素材（画像）を差し替えられる形で作る**（`data/art_spec.gd` の座標の考え方、`ui/icon_gauge.gd` などの共通部品を参照）。

## 2. 今回の作業: 建設・ワークベンチ画面の改善

### 現状（すでに実装済み。ゼロから作るのではない）

- 「建設」システムは実装済み（CLAUDE.mdの「建設と必要設備」節）。プレイヤーは **Bキー**か右の「建設 (B)」ボタンで、`ui/build_ui.gd` の画面を開く。
- この画面は **左＝建設**（拠点に設備を建てる。材料の在庫・必要設備・状態・［建設を依頼する］ボタン）、**右＝製作**（仲間が自動で作る物の一覧）の2カラム構成。
- 最初は手作業でできる物だけ。**ワークベンチ**（木材3＋鉄1）を建てると、ベッドや鉄の道具など、ワークベンチが必要な物が作れるようになる。
- 建てる処理そのもの（`Main.request_build` / `build_blocked_reason` / `finish_build` など、`scripts/main.gd`）と、設備の表（`data/facilities.gd` の `FacilityDB`）は**完成しており、変更しない**。
- CLAUDE.mdにはこう明記されている: 「検証用の簡単な画面で、見た目は後で大きく変える前提」「画面の見た目・ワークベンチの置き場所の見せ方は仮」。

### やってほしいこと

**`ui/build_ui.gd` の画面（特にワークベンチを建てる部分の見せ方）を、見た目・使い勝手の面で改善してください。** ロジック（何が作れるか、何が必要か）はそのままで、**画面の作り方だけ**を変える作業です。

具体的な方向性（CLAUDE.mdの「設計方針メモ」「グラフィック品質の方針」に準拠）:
- 文字の羅列（「木材 3/3」のような行の連続、長い説明文）を減らし、アイコン・進捗・色で「作れる／作れない」「あとどれだけ必要か」が一瞬で分かるようにする。
  - 参考になる既存の共通部品（**車輪の再発明をしないでください。**これらを使い回す前提です）:
    - `ui/item_widgets.gd`（`ItemWidgets`）: アイテムのアイコン、✓×鍵の印（`mark_ok.png` / `mark_ng.png` / `mark_lock.png`）、状態の札（色つき）。
    - `ui/qty_picker.gd`（`QtyPicker`）: 数量選択のUI部品。
    - `ui/icon_gauge.gd`（`IconGauge`）: 「アイコンそのものがゲージ」になる部品（重量・HP・拠点耐久などで使っている）。ワークベンチの組み立ての進み具合を表すのに使えるかもしれません。
    - 実は、すでに似た仕組みで **制作の画面 `ui/craft_ui.gd`** が今回のアイテム・インベントリ・制作システム（`CLAUDE.md`の「アイテム・インベントリ・制作システム v0.1」節）で実装されています。「作れる／作れない」を色・印・アイコンの暗さで見せる作りは、すでにそこにあるパターンです。**同じ見せ方の作法を、建設・ワークベンチの画面にも広げる**、という位置づけで進めてください（画面を統合する必要はありません。作法だけ揃える）。
- ワークベンチが組み立てられていく過程（依頼中 → 材料集め中 → 運搬・組み立て中 → 完成）を、文字の状態表示だけでなく、視覚的に伝える（進捗ゲージ・アイコンの変化など）。
- 「建設できない理由」（必要設備がない・材料が足りない・満杯で依頼できない、など）を、赤い印や暗いアイコンなど、既存のアイテム・制作画面と同じ視覚言語で見せる。

### 変更してはいけないもの

- ゲームのロジック・数値（設備の費用 `FacilityDB`、建設の進み方、必要設備の判定、`GameData.RECIPES`）。
- 既存のキー操作（**Bキー = 建設**。右のボタンの並び。下記4章のY座標を参照し、他のボタンと重ならないこと）。
- 「部屋の変更」（Rキー・`ui/base_ui.gd`）は別システムなので触らない（建設＝部屋の中に設備を足す、部屋の変更＝区画そのものを変える、の役割分担はそのまま）。
- 他の画面（インベントリ Tab・制作 F・仲間の管理 C・運営の方針 P・遠征 X・部屋の変更 R）の動作。

## 3. 作業の進め方（このリポジトリの共同作業ルール）

このリポジトリは、PC側のClaude・スマホ（クラウド）側のClaude・そして今回のGPTが、**同じフォルダを別々の作業者として編集**します。事故を防ぐため、次のルールを守ってください。

1. **`main` が正本**です。作業を始める前に、必ず最新の `main` を取り込んでください。
2. **直接 `main` に push しない。** 新しいブランチを切って作業してください。ブランチ名は `gpt/<内容>` の形（例: `gpt/build-ui-workbench`）。
3. **ファイルを丸ごと書き直さない。** 既存のファイル（`ui/build_ui.gd` など）は、必要な箇所だけを編集してください。「使われていなさそう」「重複していそう」に見えるファイルも、勝手に消さないでください（実際には別の場所から使われていることがあります）。
4. 作業が終わったら、`CLAUDE.md` の一番下にある「**作業ログ**」の節に、日付・環境（「GPT」と書く）・何をしたか・未完了の点を1〜3行で追記してください（他の環境の記録と同じ書式）。
5. **`main` へは直接pushではなく、Pull Request（PR）にしてください。** ユーザー本人が内容を見てマージします。
6. コミットメッセージ・PRの本文には、あなたが作業したことが分かる形で署名してください（Claude用の「Co-Authored-By: Claude Sonnet 5」は付けないでください。それはこの環境のPC側Claude用の署名で、あなたの作業には当てはまりません）。

## 5. 確認してほしいこと（提出前に）

CLAUDE.mdの「実装後は以下を確認する」と同じ内容です:

1. Godot 4.7.2で起動する（エラーなし）
2. 既存の仲間AIが動く（採取・運搬・加工・修理・休憩）
3. 資源回収・運搬・加工が動く
4. 優先度変更（★）が動く
5. 仲間詳細画面（Cキー）が動く
6. 建設（Bキー）で、ワークベンチが実際に建つところまで通しで確認できる
7. 変更が、他の既存機能を壊していない

ヘッドレスでの確認方法（Godotコマンドがある場合）: `Godot --headless --import --path .` のあと `Godot --headless --path . --quit-after 300` を実行し、`error` / `warn` が出ないか確認してください。既存の自己診断ツール `tools/test_build.gd` も、変更後に壊れていないか実行してください:
```
Godot --headless --path . -s res://tools/test_build.gd
```
「すべて成功」と出れば既存の建設ロジックは壊れていません。
